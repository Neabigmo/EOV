## 1｜AncSR1 档案：三条对既存记录的更正

### 1.1 ❌ 更正一：deposit 有 **184** 个文件，不是 20 个

`M0_license_and_novelty.md` 与 `PROVENANCE_LEDGER.csv` 都记着"20 个 `.rda` + 1 个 `.gexf`，**没有 CSV**"。
**该结论只读了 Dryad API 的第 1 页。**

| 项 | 实测 |
|---|---|
| 文件总数 | **184**（API `total=184`，10 页） |
| 总字节 | **6,312.2 MB** |
| 扩展名 | `.rda` **181** / `.gexf` **2** / **`.md` 1** |
| 那一份 `.md` | **`README.md`（13,670 B）—— 完整 schema 文档** |

→ **"没有文档、需 R 才能读懂"这一判断是错的**：README 逐对象写明了全部语义。
→ 本轮**先读了 README 再碰数据**，AncSR1 的全部结构由此确定，未依赖任何猜测。

### 1.2 ❌ 更正二："`{ERE,SRE} × 2 背景`"里的"2 背景"在本 deposit 中**不存在**

`AMENDMENT-002 B-3`、`DATA_AUDIT.md`、`PROVENANCE_LEDGER.csv` 均记 AncSR1 为
"4 位点完整 20⁴ = 160,000 × {ERE, SRE} × **2 背景** × 2 重复"。

实测（**只比基因型集合与缺失模式，不看表型值**）：

| 检查 | 结果 |
|---|---|
| `DT.JOINT` 的 4-mer 集合 | 160,000 |
| `DT.11P.CODING` 的 4-mer 集合 | 160,000 |
| 交集 | **160,000（Jaccard = 1.0000）** |
| `sequences`/`pos` 逐行是否相同 | 是 |

→ 两个对象的基因型空间完全重合。所谓"两个蛋白背景"在本 deposit 里**没有对应的两套条件**。

### 1.3 ⚠️ 更正三：`DT.JOINT` 与 `DT.11P.CODING` **不是**同一批数据的两种形态

用**缺失模式**判定（结构性证据，不涉及表型）：

| RE | 缺失模式一致率 | `DT.JOINT` 独有已测 | `DT.11P.CODING` 独有已测 |
|---|---|---|---|
| E | **0.9031** | 3,231 | 12,269 |
| S | **0.9202** | 2,007 | 10,760 |

→ 两者互为**部分重叠但互不包含**的库。
→ 因此**最宽松的读法**是 4 个条件 = {库A, 库B} × {ERE, SRE} → C(4,2) = **6 对**。
→ **本报告同时按两种读法判定，结论不变**（见 §2）。

### 1.4 Dryad 取数：端点与反爬的实测结论

| 端点 | 结果 |
|---|---|
| `/api/v2/files/{id}/download` | **401** `{"error":"Unauthorized, must have current bearer token"}` |
| `/downloads/file_stream/{id}` | 200，但是 **Anubis 1.24.0 proof-of-work 挑战页** |
| `/api/v2/...` metadata | 正常 |

**对照实验（排除"'未发布'导致"这一假设）**：已发布的 Bank2016 `th0rj` **同样返回 401**。
→ 401 是本端点的通性，不是 AncSR1 的状态问题。

**解法**（`eov/m6_dryad_client.py`，协议自本站 `main.mjs` 与 `sha256-webcrypto.mjs` 反读，非猜测）：
`solve nonce: sha256(randomData + str(nonce))` 前 `difficulty` 个十六进制位为 0，
再 `GET .../pass-challenge?id=&response=&nonce=&redir=&elapsedTime=` 取票。
实测 difficulty=4，**5–123 ms 解出**，此后全部文件可下。
（挑战页内埋有 honeypot 链接，实现**从不跟随页面内任何 `<a href>`**。）

## 4｜🔴 未决冲突：`Wu2020` 与既有冻结分类矛盾（**需用户裁决**）

`Wu2020` 满足 `AMENDMENT-017` §6 的全部六条：

| 判据 | 实测 |
|---|---|
| E1 task 数 ≥3 | **7**（`Bei89, Bk79, Bris07L194, Bris07P194, HK68, Mos99, NDako16`） |
| E2 pair 数 ≥10 | **C(7,2) = 21** |
| E3 空间可定义 | 完整 **4·4·3·2·3·2 = 576**，观测 576 |
| E4 Hamming-1 | 度 **12** = (4-1)+(4-1)+(3-1)+(2-1)+(3-1)+(2-1) |
| E5 graph_eligible | 多任务 + 组合邻域俱在 |
| E6 OP-21 档 ≥2 | cap = 144 → **[24, 96]** |
| OP-18 | **7 个任务缺失率全部 ≤25%**（抽查两文件为 0.0000） |

### ⚠️ 但是：

**`DATA_AUDIT.md` §2.6 的分类表已把 `Wu2020` 明确列入
`oracle-only（空间过小，OP-21）`。**

而 `OP-21` 的**规则原文**（`AMENDMENT-002 B-2`）是**逐档**的：

> 「**`B ≤ |space| / 4`**（coverage ≤ 25%）。任何数据集/任务违反此式时，**该 `B` 档位**不得使用。」

按规则原文，`576/4 = 144` → `B ∈ {24, 96}` 合法，只有 `384` 档被剔除 →
**`Wu2020` 应可用**；按分类表，它已被判 `oracle-only`。

> **我不单方面解封它。** 理由：把 `Wu2020` 从 `oracle-only` 解封，
> 恰好等于"为了拿到一个确认集而推翻一条既有冻结分类"——
> 这正是整个预注册纪律要防的动作，**必须由用户裁决**。

### 4.1 若解封，`Wu2020` 仍带三项未决风险（须一并权衡）

1. **空间过小 / coverage 过高**：`B=96` 时 coverage = **16.67%**，
   对照 M4 已报的 TEM-1 **0.694%**、Phillips **0.586%** —— 高 **7–28 倍**。
   OP-21 的立法意图是"不能把空间买下来"；16.67% 虽在 ≤25% 内，但语义上已远离"预算型搜索"。
2. **任务轴的性质**：7 个任务 = 流感 H3N2 的 **7 个毒株背景**（1968–2016）。
   与 TEM-1 的"换底物"、Phillips 的"换环境"同类（换遗传背景），但与 M5 的发现集**机制不同**，
   解释力方向未经验证。
3. **provenance 未落账**：GraphFLA 是**第三方整理版**（ledger 中 `GraphFLA_corpus` 角色为 `oracle_only`，
   且 `C8-2` 规定其"不得再打包"）；`Wu2020` 的**原始 deposit 未登记进 `PROVENANCE_LEDGER.csv`**，
   也未核 license；且 GraphFLA 整理版**只有单一 `fitness` 列、无 SEM**，
   而 CL-9 的 `informative_frac` 与整个 EOV 噪声模型都需要 `value_sem`。
   → **若采用，必须先回原始 deposit 取数、核 license、登记 ledger。**
